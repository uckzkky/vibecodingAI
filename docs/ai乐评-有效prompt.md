## 2. 产品定义（做什么）

**指令原文（意译合并）**

> 做一个**音乐相关智能体**：输入**歌名 + 歌手**，抓取网页链接，智能总结：**乐评、创作背景、针对这首歌/同期的采访、采样来源、乐器、MV 与视觉作品**。

**后续收窄（仍影响成品）**

> 先**不管采样**，专注给**一个歌手或一首歌做乐评**。  
> 重点在**更小众的音乐**（示例：**lufive《2008》**）。**不要查百度/维基这类科普百科**，要**垂直领域**检索。乐评不要简单摘抄豆瓣，要**更专业的分析路径**（后演化为：社媒听众 + 中文平台长评/乐评博主 + 单独一段 AI 乐评，而非外国机构爬取）。

**落地**

- 编排从「六段百科式报告」演进为：**听众社媒 → 影音测评 → 创作理念/采访/MV → AI 乐评**；采样/乐器/WhoSampled 从 live 路径退出。

## 3. 交互形态

**指令**

> 要**网页用户端口**，类似 DeepSeek：输入问题得到回答，但回答要是**更丰富的报告**，带**动态效果**。  
> 产品名改为 **vibe乐评**；去掉「试试示例」等演示按钮，**只在聊天框保留输入**；不要叫「单曲资料」；**用 AI 写一段真正的乐评**（不是只堆检索摘要）。  
> AI 乐评要**更详细**，是对社媒评价的**分析**，不要整篇都是**统计句**。  
> 页面**做好看一些**；效果要**更有动态感**。

**DeepSeek**

> 希望接入 **DeepSeek**，并说明怎么配 `.env`（密钥只写在本地环境，不进文档）。

**落地**

- `web_app.py` + `index.html`，SSE `/api/ask`；`write_ai_review` + `review_prompt.md`；打字机乐评、状态时间线等。

## 4. 信息架构与内容块（听谁说、从哪挖）

**指令（合并多轮）**

> 检索范围不对、深度不够：要在**各种社媒**上搜对该歌手/歌的评价，**第一块**用**词云/热点**呈现。  
> **还要豆瓣**；要看**不同平台对评价的差异/偏移**。  
> **锚点始终是歌手和歌曲**：外界评价、**创作理念**、采访、**乐评人**；**B 站、豆瓣、抖音**上视频博主评歌也是素材。  
> **按这个逻辑改**（四层外界声音 + 影音测评，而不是百科堆叠）。

**专业乐评步骤调整**

> 轨迹里的 **`analyze_criticism`（外国专业机构乐评）删掉**——很多中文歌手没有外国机构乐评是正常的；改为爬/搜 **B 站乐评博主、豆瓣与网易云长评**。

**平台裁剪**

> **删掉微博和知乎**；**它们上面那一整块**（总关键词/总词云一类）也删掉。

**落地**

- `social_cloud`（网易/豆瓣/B 站 + 小红书摘要）；`find_video_reviews`；`report`/`index.html` 分平台词云与情感卡片；外国乐评不再进 live loop。

## 6. 数据与检索质量（你点名的 bug → 改法）

**词云只有「两个字」**

> 关键词提取不应固定成两字，要抽**真正的词**。

**情感卡片缺 B 站**

> 新测时**感情卡片没有 bilibili**（评论少也要合理展示）。

**B 站查偏（蓝猫例）**

> B 站明明有很多评歌/电台内容，却只抓到几条——**查询范围不对**；问**以后检索怎么避免**同名动画/无关 UP 主干扰。

**厂牌 + 歌手一句话输入**

> 要能一句话搜 **某厂牌下的某歌手**，例如「厂牌旗下的歌手」句式。

**落地**

- `social_cloud.py` 分词/过滤、B 站多 query + on/off topic；`parse_request` 厂牌模式；`sentiment` 与 `drift` 阈值拆分；情感卡 B 站 ≥3 条即展示。
